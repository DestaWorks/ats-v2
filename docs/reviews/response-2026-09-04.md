# Code review response — 2026-09-04

Four findings raised against `feat/p6-hardening-and-containerisation` (PR #67). Each was checked
against the code rather than accepted or dismissed. **Three were correct and are fixed; one was
already fixed on a newer revision, but the caution behind it was right.**

All 11 CI gates green after the changes.

---

## 1. Deploy gate missing the tenant-isolation check — correct, fixed

**Raised as:** high priority, one-line fix. Nothing stops a deploy shipping a revision where the
cross-tenant-leak proof failed.

**Confirmed.** `deploy.yml` required four checks — Commit messages, Static analysis, Tests, Build.
`Tenant isolation` is the only job that proves tenant A cannot read tenant B, per table, against a
real Postgres, and it was not among them.

`Tenant isolation` is now required in both places that list the checks: the API query that reads
their conclusions, and the loop that asserts each one is green.

Worth naming plainly: this gap was **already written down** in `DECISIONS.md` D6 during the
documentation pass and never actioned. Recording a hole is not closing one. The reviewer was right
to put it first.

---

## 2. Rate-limit fallback unbounded — already fixed, and the question was the right one

**Raised as:** only bites if `REDIS_URL` is unset in production; confirm Redis is actually required
at deploy time first.

**Already fixed** in `5d87103` — the in-memory map now evicts entries older than an hour once it
passes 20k keys. The review was against an earlier revision.

**Answering the question directly: `REDIS_URL` is _not_ required at boot.** It is optional by
design, because the in-memory limiter is exact for a single process — the count is accurate and the
window slides. So the fallback path is genuinely reachable in production, not merely a dev
misconfiguration. The caution was correct even though the specific defect was gone.

It is bounded either way now, and Redis is wired into `docker-compose.yml` for the point at which a
second instance exists — which is when the fallback stops being correct, silently, because every
limit becomes `limit x instances`.

## 3. TOCTOU invite race — correct, fixed

**Raised as:** medium. Needs an invite and the user's own accept in the same window. No privilege
escalation; worst case an active member is silently bounced back to `invited`.

**That read is exact.** `invite` read for an existing active membership and then upserted — two
statements, with an accept able to land between them and be overwritten.

Fixed by moving the guard **into the write** rather than widening the transaction around it. The
upsert's `where` now carries `status: { not: "active" }`, so the condition is part of the same
statement. Prisma treats an unmatched `where` as a create, which the `@@unique([tenantId, userId])`
constraint then rejects — **a refused invitation rather than a lost membership**, which is the
right direction for this to fail in.

## 4. Cross-tenant admin blast radius — correct, worse than described, fixed

**Raised as:** push toward high; likely covered by the 6.4 role plan already noted in the docstring.

**Correct, and it is _not_ covered by that plan.** 6.4 concerns `User.role` — a column this app
still writes because Better Auth's admin plugin gates its own endpoints on it. This finding is a
different thing: `removeUser`, `banUser` and `setUserPassword` are **global operations**.

| operation | effect |
| --- | --- |
| `removeUser` | deletes the account — removes them from **every** workspace |
| `banUser` | locks the account everywhere |
| `setUserPassword` | changes the one password the account has |

An earlier fix scoped the **lookup** — the target had to hold a membership in the acting workspace.
It did not scope the **effect**. Those are different problems, and only the first was solved. An
Owner of workspace A could still delete an account that also belonged to workspace B, and
`membershipRepository.listByUser` confirms multi-workspace membership is real rather than
theoretical — it is what the workspace switcher runs on.

The guard now also requires the account to belong to **no other live workspace**. When it does, the
call returns `CONFLICT` with a message pointing at `membershipService.removeMember`, which ends the
membership and leaves the account intact — the operation that screen actually wants for a shared
user.

Six tests were added, one per global operation, plus a case proving a membership already `removed`
elsewhere does not block the action.
