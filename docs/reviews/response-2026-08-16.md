# Response to 2026-08-16 code review

Every claim below was checked directly against the current codebase (and, where relevant, live
Vercel production config) — not accepted from the review's own summary. See `docs/DECISIONS.md`
for the standing rule that security-sensitive items go through the Owner.

## Code-quality findings (F1–F10)

All 10 confirmed real. Ranked by severity, with the exact mechanism (sharper than the review's
summary in a few places):

- **F1 (HIGH)** — Bulk lead "status" action can set a lead's status to `"Promoted"` directly,
  bypassing the real `promote()` flow entirely. No `Candidate` gets created, `promotedCandidateId`
  stays null — an orphaned "Promoted" lead. `server/services/lead.service.ts`.
- **F2 (MEDIUM)** — CSV export has no formula-injection guard: `escapeCell` only handles RFC4180
  quoting (`"`, `,`, newlines), nothing for a leading `=`/`+`/`-`/`@`. A candidate name starting
  with one of those lands in the exported CSV unescaped. `lib/reports/csv.ts`.
- **F3 (MEDIUM)** — Portal-access approval is a real, unguarded TOCTOU race when no `contactId` is
  supplied: two concurrent approvals can each create a `ClientContact` (no unique constraint on
  the table) and each mint a live portal token. `server/services/portal-access-request.service.ts`.
- **F4 (MEDIUM)** — Real IDOR: the role-note delete route receives both `roleId` and `noteId`, but
  `roleId` is dropped before it reaches the repository's `where` clause, which scopes only by
  `noteId`. Any operator can delete any role's note by pairing it with an arbitrary (existing)
  roleId. Also corrupts the audit trail. `server/repositories/open-role.repository.ts`.
- **F5 (MEDIUM)** — ETL AI résumé-attach has no idempotency key, unlike the candidate/document
  upserts next to it (which are keyed on `legacyId`). Re-running a bulk-import commit re-attaches
  and duplicates PII-bearing `Document` rows. `server/services/migration.service.ts`.
- **F6 (LOW)** — "Since you closed" recap counts come from `.length` of capped arrays (50/50/100
  row `take` limits), not a real `count()` — undercounts once real volume exceeds the cap.
  `server/services/daily.service.ts`.
- **F7 (LOW)** — `markRead` looks up the mention inside a 20-most-recent page instead of by its own
  id; an already-read mention older than that page falsely throws `NOT_FOUND`, contradicting the
  method's own "idempotent no-op" doc comment. `server/services/mention.service.ts`.
- **F8 (LOW)** — Résumé `save()` has no idempotency guard and nothing at the DB level either
  (`Candidate.email` has no unique constraint) — two concurrent saves for an email-less candidate
  can each independently create a new Candidate + Document. `server/services/resume.service.ts`.
- **F9/F10 (LOW)** — Confirmed and precisely bounded: the DB-level "stuck" filter uses a raw
  millisecond threshold (flips at exactly 7.0 days), the per-card badge uses `Math.floor(days) > 7`
  (flips only after a full 8th day) — DB is "ahead" of the UI badge by up to ~24h.
  `server/repositories/candidate.repository.ts` vs `lib/rules/stage-timing.ts`.

Also confirmed: the server-only-guard gap (`server/http/app-error.ts` is the one *unintentional*
miss — the other 3 files without the import are deliberately-documented pure/isomorphic
exceptions), and the ESLint zones gap (`src/app` genuinely isn't covered by the import-boundary
rule, only `src/modules`/`src/lib` are).

## Corrections to the review

**H3 ("no password-reset flow exists") is wrong — already implemented and live.** A complete
forgot-password → email → reset-password flow exists: `/forgot-password` and `/reset-password`
routes, wired to Better Auth's `requestPasswordReset`/`resetPassword` client methods and the
server-side `sendResetPassword` hook, linked from the sign-in page. Merged to `main` (commit
`3b844ab`, 2026-08-08). `docs/SECURITY-AUDIT-APP.md` still lists this as open because that doc is
dated 2026-07-18 — three weeks before the fix landed. The doc needs its H3 entry updated to ✅
Fixed; flagging separately rather than editing it unprompted.

**H2 (encryption key/coverage) is accurate — verified directly, not assumed.** Checked live via
`vercel env ls production`: `FIELD_ENCRYPTION_KEY` was genuinely not set. Checked the repository
layer directly: only `candidate.repository.ts` (`licenseNumber`) and `document.repository.ts`
(résumé `extractedText`/`extractedData`) call `encryptField`/`decryptField` — email, phone, NPI,
and notes have no encryption code path at all, exactly as the review states.

Update: the key has now been generated and set in production. It activates encryption for new
writes to the 2 wired fields on the next deploy. Two things still open, both Owner-scope: whether
to expand encryption to email/phone/NPI/notes (real engineering work, not just a config change),
and backfilling existing plaintext rows (nothing retroactively encrypts on its own — only rows
written after the key is active get encrypted).

**`audit.repository.ts`'s `listForEntity` is NOT unbounded**, contrary to the review's §2.2 claim
— it already has a 200-row cap (`ENTITY_TRAIL_CAP`), added in an earlier perf pass (2026-08-03),
predating this review.

## Already implemented (not visible in the review's source branch)

- **H6 — persistent rate limiting.** Implemented: Upstash Redis-backed limiter, real cross-instance
  protection, with an in-memory fallback only when unconfigured. Fails open on a Redis error rather
  than hard-failing requests.
- **Connection pool tuning.** `prisma.ts` now caps the pool at `max: 5` per serverless instance
  (was unbounded, defaulting to node-postgres's 10).
- **Candidate-scoring re-fetch (§2.2).** `ClientRules` reads are now request-cached
  (`cachedClientRulesList()`), matching the existing `cachedClientList`/`cachedUserList` pattern —
  no more re-fetching the full rules table on every sibling read in the same request.

Pull the latest branch to see all three.
